# 기술 스택 선정 (목업 단계)

## 선택: Vite + React + TypeScript (+ react-router, vitest)

| 구성 | 용도 |
|---|---|
| Vite | 로컬 개발 서버·빌드. 설정이 거의 없고 `npm run dev` 한 번으로 실행 |
| React | 화면을 재사용 가능한 컴포넌트로 구성. 목업 화면을 실서비스에서 그대로 이어 쓸 수 있음 |
| TypeScript | 직원·평가표·배정·응답·계산 정책의 **데이터 계약(타입)**을 코드로 고정. 실서비스 DB 스키마의 초안이 됨 |
| react-router (HashRouter) | 화면 이동. 해시 주소라 서버 설정 없이 로컬·정적 파일로 열 수 있음 |
| vitest | 단계 잠금·진행 집계·개발용 계산 같은 핵심 로직의 자동 테스트 |
| 브라우저 localStorage | **목업 전용 가상 저장소.** 한 브라우저 안에서만 유지되며 서버 저장이 아님 |

## 왜 이 조합인가

1. **35명 규모에 맞는 단순함**: 별도 서버·DB 없이 로컬에서 바로 검토할 수 있다. 유료 서비스·외부 배포가 필요 없다.
2. **목업을 버리지 않는 구조**: 화면은 `src/data/store.ts`의 저장 함수만 호출한다. 실서비스 단계에서는 이 저장 계층을 서버 API(DB·인증)로 바꾸고 화면·타입·계산 로직은 재사용한다.
3. **변경에 강한 데이터 중심 설계**: 평가 방향·단계·문항 유형·영역·가중치를 화면 코드에 고정하지 않고 데이터(템플릿·회차 설정·계산 정책)로 둔다.
4. **팀이 배우기 쉬움**: React·TypeScript는 자료·예제가 많고, 교육 과정 팀원이 이어서 유지보수하기 쉽다.

## 검토했지만 지금은 택하지 않은 안

- **순수 HTML/JS 한 파일**: 가장 단순하지만 실서비스로 이어 쓰기 어렵고 타입·테스트가 약하다.
- **Next.js 풀스택 + DB 즉시 구성**: 실서비스에는 후보가 될 수 있으나, 규칙이 미정인 지금 DB·인증부터 만들면 검토 전에 구조가 굳는다.

## 실서비스 단계(목업 검토 후 결정할 것)

- 서버·DB: 관계형 DB(PostgreSQL 계열)를 권장. Supabase는 후보로 언급됐을 뿐 확정 아님. 회사 소유 계정, 요금제·약관 확인일 기록 후 결정.
- 인증: 관리자·대표자 별도 로그인, 직원은 개인 토큰 링크 + 사번 확인(서버 검증, 토큰 해시 보관, 만료·재발급).
- 파일: 서버에서 권한 검사 후 XLSX·PDF 생성.
- **localStorage만으로 실제 여러 직원의 응답을 저장하지 않는다.**
